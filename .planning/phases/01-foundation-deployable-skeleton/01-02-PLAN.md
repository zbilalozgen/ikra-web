<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| developer machine → GitHub | `gh` CLI uses an already-authenticated token to create and push to a remote repo |
| developer browser → Vercel dashboard | OAuth handshake authorizes Vercel to read the GitHub repo and listen for push events |
| GitHub push event → Vercel build runner | Webhook triggers `npm run build` on Vercel's infrastructure; build output served from Vercel CDN |
| internet visitor → Vercel CDN | Public read-only access to the static skeleton |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information Disclosure | first commit pushed to GitHub | mitigate | Verify `.gitignore` excludes `.env*` and `.next/` before first commit; gate this in Task 1's automated verify (`git ls-files` must not match `.env` or `.next/`). No secrets are introduced in Phase 1 (static site, no API keys). |
| T-02-02 | Spoofing | GitHub repo ownership | accept | `gh repo create` runs under the operator's authenticated `gh` identity (verified via `gh auth status`). Repo ownership matches the human operator. |
| T-02-03 | Tampering | Vercel ↔ GitHub OAuth integration | mitigate | Human-action checkpoint (Task 2) — operator personally authorizes the integration in their own browser session against vercel.com; no automated token handoff. |
| T-02-04 | Denial of Service | Vercel default subdomain | accept | Vercel's free-tier CDN provides DDoS protection at the edge; static site has no compute path to exhaust. |
| T-02-05 | Elevation of Privilege | Vercel build runner executing repo code | mitigate | Build command is locked to `npm run build` (Next.js default); no custom post-install scripts or shell hooks introduced in Phase 1. |
</threat_model>
